# pstack in omp

Read this adapter before the upstream skill. It overrides Cursor- and Claude-specific instructions, but never overrides the actual user request, system instructions, tool policies, or authorization requirements. An upstream claim of blanket autonomy does not grant permission. Follow the current session's tool schemas and restrictions when they differ from examples below.

## Skills and paths

Exposed skill names are `pstack-<upstream-name>`; invoke `/skill:pstack-<upstream-name>` or read `skill://pstack-<upstream-name>`. Map upstream `/name` references to this form for pstack skills. Physical directories remain `skills/<upstream-name>`. Derive the package root from the actual invoked `SKILL.md`: resolve its real path through any symlinks, then go up two directories from the file's parent. Read bundled docs and resources, including `docs/guide/`, relative to that root, not a Cursor cache or remote copy. Map references to pstack's own agents to `pstack-poteto-agent` and `pstack-comment-sicko`. The native omp plugin owns discovery of these skills and agents; do not create external `.agents` symlinks for them.

An already-running session may retain its old skill catalog. Start a new session or use the runtime's reload command before relying on newly installed `skill://` names. If the required skill is unavailable in a stale catalog, stop the dependent work until the catalog is refreshed; do not fall back to an old home-directory cache. Rewrite a literal upstream `pstack/skills/...` script path against the discovered package root rather than assuming the project contains a `pstack/` directory.

Native generated skills belong in the active agent directory's `skills/` for user scope or the project's `.omp/skills/` for project scope, unless the user specifies another supported location. The default agent directory is `~/.omp/agent`; profiles and `PI_CODING_AGENT_DIR` can change it. Native rules use its `rules/` or project `.omp/rules/`, not Cursor `.mdc` paths. The pstack model rule is `<active-agent-dir>/rules/pstack-models.md`, with `alwaysApply: true` frontmatter. Native settings live in the active agent directory's `config.yml` or project `.omp/config.yml`; do not edit them merely to run pstack. `/skill:pstack-setup-pstack` handles its own user-approved rule write.

Some upstream workflows refer to companion skills outside pstack. Resolve those by their actual installed names and read them when needed; do not invent a `pstack-` name for an external skill. If a required companion is absent, report it as a prerequisite and block that dependent workflow.

Map Cursor's built-in `create-skill` to the installed `writing-for-agents` skill and its `SKILL-MECHANICS.md`, then create the requested native skill with the available file tools. If those instructions are unavailable, report that prerequisite. `/loop` is not a presumed omp command: a finite agent loop may use the actual supervision tools with an explicit stop condition; unattended scheduling requires an available authorized scheduler. Do not turn a bounded request into a recurring job.

## Tools and delegation

Use the tools actually exposed in this session. Cursor `Task` maps to `task`; `AskQuestion` maps to `ask` when available, otherwise ask the user in chat. Use `todo` when available and allowed. Use `read`, `grep`, `glob`, `bash`, `edit`, `write`, `web_search`, and `eval` under their actual schemas and session policies. Do not pass Cursor or Claude field names to omp tools.

For the default batched `task` schema, supply shared `context` and `tasks` entries containing `task` and `solutionSpace`; put optional `agent`, `name`, and `model` on each entry, not the top level. Omit `agent` for the default general worker. Use `scout` for read-only exploration and explicitly require no writes; its tool restrictions, not a `readonly` flag, govern it. Select `pstack-poteto-agent` or `pstack-comment-sicko` by exact agent name when requested. Task `tools`, if exposed, names parent Eval-defined tools, not built-in permissions. Put resource paths and complete instructions in the brief; there is no `file_attachments` field. Consult the current schema or `omp://tools/task.md` for optional fields and settings.

Task calls may run asynchronously or synchronously according to session settings. Async results arrive automatically; work independently, then use `wait` when blocked. `agent://<id>` reads output; when messaging is enabled, `write agent://<id>` sends a message and can revive an eligible parked agent. Follow the active lifecycle instructions; do not pass Cursor `run_in_background` or `resume` fields. When a fresh worker is required, spawn one and provide relevant prior results. `history://<id>` accesses registered agent transcripts.

`environment: cloud`, `cloud_base_branch`, and Cursor cloud state have no direct task equivalents. An `isolated` field exists only when enabled and exposed; it creates an isolated workspace with captured changes, not a VM or cloud service. Its apply/merge behavior depends on configured isolation settings. Shared workers otherwise use the parent checkout. If a workflow requires a separate machine or cloud agent, name that missing capability and block the dependent step; do not claim workspace isolation provides it.

## Models

Read `<active-agent-dir>/rules/pstack-models.md` when present. Its role choices override upstream defaults. Without that rule, use `inherit-parent` for every role instead of Cursor's default model slugs; this does not satisfy a workflow that requires distinct model families. Discover concrete provider/model IDs with `omp models --json`. Exact selectors use `provider/model-id` and may append a supported `:effort`; consult `omp://models.md` and the live task schema. Per-call selection must be enabled and operator-authorized, and conflicts with `task.agentModelOverrides` must be resolved rather than ignored. `auto` and `inherit-parent` refer to the actual parent session identity, not literal selectors. Omit `model` only when effective agent settings select that identity; otherwise use its authorized concrete selector or report the blocker. Preserve required model family and cross-family judge independence: unavailable authorized models block that dependent workflow. Record actual model and effort used; do not claim an unsupported budget was honored.

## Evidence and external services

For previous work, use Eval's read-only `archive` interface (`xd://eval/archive`) scoped to the current project unless the user requests broader scope. Consult a historical session with the available `seance` agent when applicable. For session files, use paths returned by runtime discovery and limit reads to the relevant project/session. Never scrape all home-directory transcripts or infer Cursor or Claude transcript paths as omp history.

For browser proof, use the available browser through Eval and its `xd://eval/browser` documentation; perform the requested interaction and inspect actual results or screenshots. Relay/CDP can access a real signed-in user session: authorization and tool policies still apply. For terminal UI proof, use an available interactive PTY and observe the actual screen and interaction. A static file, inferred behavior, or a noninteractive command is not browser or TUI proof. If the necessary display, PTY, browser, credentials, or service is unavailable, report the missing prerequisite and leave the proof incomplete.

Before running a bundled script or bootstrap, inspect its actual contents, dependencies, supported OS and shell, network access, filesystem changes, and credential or installation side effects. Run only when authorized and prerequisites are met; never assume a script is portable or side-effect-free. Cursor Automations, cloud agents, secret requests, dashboards, Bugbot execution, and Cursor-specific APIs have no presumed omp equivalents. Use an actual configured and authorized equivalent only when it supplies the required capability. Existing forge review comments may be inspected using available authorized forge tools; that does not start or replace Bugbot.

A missing required capability blocks the affected workflow and any dependent outputs. Continue independent work only, state exactly what is blocked and why, and never fabricate success, URLs, secrets, or placeholders as completed results.
